# 직원관리 시스템 요구사항 정의서

## 1. 과제 목표

기존 직원 구성도 ERD/DDL을 PostgreSQL에 올리고, 그 데이터를 사용하는 직원관리 웹사이트를 구현한다.

중요한 평가지점은 다음이다.

- 기존 ERD/DDL 이해
- PostgreSQL 저장
- 필수 CRUD 구현
- 재직/휴직/퇴직 상태 변경
- 상태 변경 이력 저장
- Plan First 방식과 Claude Code 활용 과정 정리

## 2. 기능 요구사항

### F-01. 직원 목록 조회

직원 목록을 표 형태로 보여준다.

최소 표시 필드:

- 사번 또는 직원 ID
- 이름
- 이메일
- 부서
- 직책
- 직속상사
- 재직상태
- 입사일

상태는 배지 형태로 표시한다.

| 코드 | 표시 | 의미 |
|---|---|---|
| `ACTIVE` | 재직 | 정상 근무 중 |
| `LEAVE` | 휴직 | 복직 가능 |
| `RESIGNED` | 퇴직 | 종료 상태 |

### F-02. 직원 등록

직원 정보를 입력해 PostgreSQL에 저장한다.

필수 입력:

- 사번
- 이름
- 이메일
- 부서
- 직책
- 재직상태
- 입사일

선택 입력:

- 전화번호
- 직속상사
- 메모

### F-03. 직원 상세 / 수정

직원 1명의 상세 정보를 조회하고 수정할 수 있다.

수정 가능한 필드 예시:

- 이름
- 이메일
- 전화번호
- 부서
- 직책
- 직속상사
- 메모

사번은 중복 방지를 위해 원칙적으로 수정하지 않는다.

### F-04. 상태 변경

상태 전환 규칙은 다음과 같다.

| 현재 상태 | 변경 가능 상태 |
|---|---|
| `ACTIVE` | `LEAVE`, `RESIGNED` |
| `LEAVE` | `ACTIVE`, `RESIGNED` |
| `RESIGNED` | 없음 |

상태 변경 시 요구사항:

- 직원 목록의 상태 배지가 바뀌어야 한다.
- `T_EMPLOYEE.EMPLOYMENT_STATUS`가 변경되어야 한다.
- `T_EMPLOYMENT_HISTORY`에 변경 이력이 저장되어야 한다.
- 상태 변경과 이력 저장은 가능하면 하나의 transaction으로 처리한다.

### F-05. 검색 / 필터

선택 기능이다.

- 이름 검색
- 부서 필터
- 상태 필터

## 3. 화면 요구사항

### 목록 화면

- 직원 목록 표
- 등록 버튼
- 상세/수정 이동 버튼
- 상태 배지
- 검색/필터 영역은 선택

### 등록 화면

- 직원 등록 폼
- 저장 버튼
- 필수값 누락 또는 validation 실패 시 오류 메시지
- 저장 성공 시 목록으로 이동

### 상세 / 수정 화면

- 직원 상세 정보
- 수정 폼
- 상태 변경 UI
- 상태 변경 이력 표시 가능하면 포함

## 4. API 또는 Route 예시

스택은 자유이므로 아래는 예시다.

| Method | Path | 설명 |
|---|---|---|
| GET | `/employees` | 직원 목록 조회 |
| GET | `/employees/new` | 직원 등록 화면 |
| POST | `/employees` | 직원 등록 처리 |
| GET | `/employees/:id` | 직원 상세/수정 화면 |
| POST 또는 PATCH | `/employees/:id` | 직원 수정 처리 |
| POST 또는 PATCH | `/employees/:id/status` | 직원 상태 변경 |

## 5. Validation 기준

- 사번은 필수이며 중복될 수 없다.
- 이름은 필수다.
- 이메일은 필수이며 기본 이메일 형식을 만족해야 한다.
- 부서와 직책은 존재하는 값만 선택할 수 있다.
- 재직상태는 `ACTIVE`, `LEAVE`, `RESIGNED` 중 하나만 허용한다.
- 직속상사는 선택값이며 자기 자신을 상사로 지정할 수 없다.
- 퇴직일이 있다면 입사일보다 빠를 수 없다.

## 6. DB 기준

- 기존 `ddl/` 아래 SQL 파일을 우선 사용한다.
- 기존 DDL을 확인한 뒤 부족한 제약, FK, CHECK, seed만 보강한다.
- `F_AUDIT_LOG.sql`이 있다면 기존 감사 트리거 방식을 유지한다.
- 새 테이블을 임의로 추가하기보다 기존 `T_DEPARTMENT`, `T_POSITION`, `T_EMPLOYEE`, `T_EMPLOYMENT_HISTORY`를 우선 활용한다.
